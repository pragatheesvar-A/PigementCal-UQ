# Two reliability paths, RED, and motion = 0 (second-pass audit)

Everything below is traced from the code and re-run on the real app on 2026-10-09. Virtual data = SIMULATION; the trained/calibrated layer = SYNTHETIC test data (IMPLEMENTED — NOT RESEARCH VALIDATED); typed values = MANUAL INPUT. Real research data = 0; real validation = NOT AVAILABLE; physical hardware NOT TESTED; Wokwi NOT EXECUTED.

## Architecture (two layers, not one algorithm)
```
LIVE MONITOR                                   RELIABILITY CHECK
virtual / real sensor                          typed values (or the Live summary)
 → PPG processing, SQI, PI, estimated SpO2      → validation (ranges, missing)
 → ITA typed in the UI                          → rule engine (same points as Live)
 → RULE ENGINE  (services/reliability.py)       → supported-range check, calibration-cell sufficiency
 → GREEN / AMBER / RED / ABSTAIN                → CQR quantile models + Mondrian (ITA group × PI group) quantile
   (no calibrated interval)                     → prediction interval, lower bound, width
                                                → state = most cautious of rule engine, width, gap; or ABSTAIN
```
The Live Monitor does not call the conformal layer; the Reliability Check does not receive the live signal automatically (leaving the Live page stops the sensor, so values must be typed). The UI now says so on the Live page and in the README.

## RED: exact triggers
* **Rule engine (Live path):** points: low PI = 1, very low PI (< 0.5 %) = 2, MODERATE signal quality = 1, MEDIUM motion = 1; RED when points ≥ 3 (`red_points`). Poor signal or HIGH motion → ABSTAIN before points are counted. Reachable RED combinations: very-low PI + MODERATE quality (2 + 1), or low PI + MODERATE + MEDIUM motion (1 + 1 + 1).
* **Calibrated path:** the rule-engine state, plus interval width > 8 (`width_red`) or (reading − conformal lower bound) > 5 (`gap_red`) → RED; > 4 / > 3 → AMBER.
* **Manual case C (90 / 0.1 / 20 / 55 / 25) is RED because the gap is 90 − 84.94 = 5.06 > 5.0**, a margin of 0.06. Case B (motion score 3) has gap 4.75 → AMBER. The two cases show the same reason codes; only the gap level differs.

## Why RED appears on the calibrated manual path, and how it is now reproduced on the live virtual path
The two paths reach RED by different rules (see above), so a RED on one path does not imply the other. Originally the three-level Noise control jumped from GOOD to POOR at low perfusion, so no live scenario had MODERATE quality while PI was still computed.

**Decision implemented:** a fourth, intermediate noise level (63 counts, between low 20 and medium 120) plus a preset scenario "Low perfusion + intermediate noise". Nothing else changed: no threshold, no rule, no demo flag; the simulator does not know what RED is. The state comes from the real chain: virtual samples → `/api/live/analyze` (SQI, PI, SpO₂) → `/api/reliability/predict`. With perfusion 0.003 the computed PI is about 0.29 % (very low: 2 points) and the intermediate noise lowers the computed SQI to the MODERATE band (1 point) → 3 points → RED, reasons `low_pi, very_low_pi, moderate_signal, multiple_factors`.

Measured on 9 seeds x 8 analysis windows (72 windows): RED 40, ABSTAIN 19, AMBER 13. In the browser (seed 42, nine consecutive polls): RED x6, ABSTAIN x2, AMBER x1. The state varies because the analysis window shifts (SQI crosses the MODERATE/POOR boundary); this variation is not hidden.
Regression test: `backend/tests/test_live_red_integration.py` uses a stored 34 s window set generated by the virtual sensor (`backend/tests/fixtures/virtual_low_perfusion_intermediate_noise_seed42.json`; the frontend test `virtualSensor.test.ts` checks the generator still reproduces it byte for byte) and asserts RED with the reason codes at several window ends, AMBER/ABSTAIN at others, unchanged thresholds, and that the `virtual` label does not change the outcome.

**RED is reproducible on the live virtual path using the intermediate-noise simulation scenario.** VIRTUAL HARDWARE SIMULATION — NOT REAL MEASUREMENTS. This shows that the implemented rules can produce RED under a valid simulated condition. It is not clinical validation, does not show that any device is inaccurate, and says nothing about oxygen safety.

## motion = 0
* Without an accelerometer the motion score is a **signal-derived estimate** (`estimate_motion`): the fraction of 1-s windows whose amplitude is an outlier. A clean signal gives exactly **0.0** (API field `motion_score`, `motion_source: "estimated"`). The Live card shows it rounded (`toFixed(0)`), so "score 0" is a computed zero, not a missing value.
* The backend distinguishes missing from zero: blank → `missing_inputs` (ABSTAIN); `0.0` is a value and is only range-checked (test added).
* The calibrated layer abstains because the SYNTHETIC training data never contained 0 (its motion column is a gamma draw rounded to 0.1, so the minimum is 0.1) → "fitted range 0.1–59.4". That is a property of the synthetic data, not of the sensor or the model code. **The abstention is the designed behaviour**; do not relabel 0 as 0.1 or widen the range. Options that need your approval (methodology): (a) collect real data that includes motion ≈ 0 (the correct fix), (b) regenerate the synthetic set with exact zeros, (c) a documented tolerance equal to the score's resolution (0.1). Not implemented.
* Edge: `estimate_motion` also returns 0.0 when fewer than 3 one-second windows exist or the signal is flat. Those cases are POOR/abstained elsewhere, but the score itself does not say "unknown".

## Device label and simulation provenance
* Source `virtual` → device "Virtual ESP32 + Virtual MAX30102 (simulation)"; a real board stays "ESP32 + MAX30102". The label does not change any state, interval, cell or reason (tests: `test_the_device_label_never_changes_the_state_or_the_interval` and the live-analysis equality test).
* Recorded virtual CSV: first line `# dataset_type=virtual_hardware_simulation; research_validity=not_for_research_validation; generated_for=hardware_pipeline_integration_testing; scenario=…; seed=…`, file name `…_VIRTUAL_SIMULATION.csv`. Data Collection refuses the marker line (all four upload kinds); file/device/ID name markers make the research gate report SOFTWARE_TEST_DATA.
* **Provenance gate (hash-bound).** The gate trusts only a provenance record whose `dataset_sha256` equals the SHA-256 of the current research dataset. The record stores origin, dataset type (`synthetic`, `virtual_hardware_simulation`, ...), research validity, creation time, software version and generator version. A file name, a `#` comment line, a device label or a participant ID is never provenance: such markers can only BLOCK (check `no_synthetic_or_test_data`), and data that carries them but has no record is reported UNVERIFIED DATA. Changing one value, or copying a record next to a different dataset, makes the record not apply (`provenance_bound: false`, state UNVERIFIED_DATA). A non-human origin (`software_test`, `synthetic`, `simulated_hardware`) can never verify data. Tests: `backend/tests/test_provenance_binding.py` (7 required cases + non-human cannot verify).
* **Remaining weakness:** a stripped-and-renamed simulated recording is still accepted by Data Collection (nothing inside the data proves it is simulated) and a human provenance record is a self-declaration. What stops it from becoming a research result is that the record must be registered, complete, hash-bound and consistent with every other gate check; a false declaration is not detectable by software.

## Limits that stay
Insufficient calibration cells and out-of-range motion cause ABSTAIN (design). No thresholds, CQR, Mondrian, splits or models were changed for the virtual integration test. Signal quality varies a little between repeated virtual runs because the analysis window shifts with wall-clock timing.
